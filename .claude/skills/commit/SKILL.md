# 커밋 메시지 규칙

사용자가 `커밋 내용`이라고 요청하면 staged changes만 분석해 커밋 메시지를 제안한다. 커밋, stage, unstage는 실행하지 않는다.

이 "실행하지 않음"은 `커밋 내용` 요청에만 적용된다. 작업을 마친 뒤 직접 커밋하라는 별도 지시(사용자 지시나 메모리)가 있으면 그 지시를 따르되, 메시지 형식은 이 스킬을 따른다.

## 확인 범위

1. `git diff --cached --name-status`와 `git diff --cached`를 확인한다.
2. staged 변경이 없으면 `스테이징된 변경 사항이 없습니다.`라고 알린다.
3. unstaged 변경과 작업 트리의 파일은 메시지 판단에 포함하지 않는다.

## 형식

`<type>(<scope>): <subject> [PMS/ISSUE#]`

- `type`: 아래 표의 유형을 사용한다.
- `scope`: 변경된 기능 모듈 또는 비즈니스 도메인명. 예: `auth`, `order`, `db`, `iot`. 하나의 모듈·도메인으로 특정할 수 없는 변경(여러 영역에 걸친 문서·설정 등)은 `(<scope>)`를 생략한다(`docs: …`).
  - `pub`, `admin`, `frontend`, `ui`처럼 레이어·프로젝트·기술 범위를 나타내는 이름은 scope로 사용하지 않는다.
- `subject`: 명령형, 마침표 없이, 50자 이내로 작성한다.
- 커밋 메시지의 subject와 본문은 한글로 작성한다. `type`, `scope`, 이슈 식별자는 기존 형식을 유지한다.
- 이슈 번호는 staged 변경 또는 사용자가 제공한 정보에 있을 때만 `[PMS/ISSUE#]` 형식으로 덧붙인다. 추측하지 않는다.

| type | 용도 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `hotfix` | 운영 긴급 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `style` | 포맷팅, 세미콜론 등 로직 무관 변경 |
| `docs` | 문서 수정 |
| `test` | 테스트 코드 추가·수정 |
| `chore` | 빌드, 패키지, 설정 변경 |
| `revert` | 롤백 |
| `promote` | 운영 배포 |

## 응답 형식

독립적인 도메인 변경이 함께 staged 되어 있으면 단일 메시지로 묶지 말고, 분리 커밋을 먼저 제안한다. 각 커밋 메시지는 복사 가능한 코드 블록으로 제시한다. 공통 변경은 해당 기능 변경에 종속될 때만 함께 포함하고, 독립적이면 별도 커밋으로 제안한다.

- 커밋 메시지의 subject와 사용자에게 제공하는 안내는 한글로 작성한다. 단, Conventional Commits의 `type`, `scope`, 이슈 식별자는 기존 형식을 유지한다.

타입 또는 scope가 모호하면 근거를 짧게 밝히고, 가장 보수적인 메시지를 제안한다.

```text
feat(auth): 소셜 로그인 추가 [TSK-001]
```
